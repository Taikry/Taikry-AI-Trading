# ZYROX AI V2 — Production Risk Register

**Audit date:** 2026-10-31
**Status:** Phase 0 baseline; no production remediation was applied in this audit.

| ID | Severity | Risk and repository evidence | Impact | Required mitigation / gate |
|---|---|---|---|---|
| R-01 | **P0 / Critical — mitigated in local code; staging/deploy verification pending** | Previously, Schema Studio routes had no auth; SQL accepted a client `read_only` override; migration apply trusted a client environment string. Local code now requires admin auth on every schema route, accepts only one read-only `SELECT`/`EXPLAIN`, and derives migration environment from server config. Production apply is blocked regardless of request confirmation. | The deployed Render revision remains exposed until a reviewed revision is deployed. | Keep deploy gated until staging review. The focused local suite passed (21 tests, 2 warnings); staging review and release-revision verification remain required. |
| R-02 | **P1 / High** | Login and signup set an HttpOnly cookie but also return the raw 30-day session token in JSON (`taikry/api/saas_routes.py`); `get_current_user` accepts that token as Bearer/header credentials. | XSS, browser logging, or client telemetry can capture a bearer credential despite HttpOnly cookie settings. | Stop returning raw tokens to browser clients; use cookie-only web sessions or a deliberate short-lived token design. Add tests that response JSON cannot contain the token; inspect frontend compatibility before migration. |
| R-03 | **P1 / High** | `init_db()` is called at `taikry/database/session.py` import time and again in FastAPI lifespan; it creates tables and runs multiple hand-written migrations during app startup. | Slow/colliding startup, non-atomic rollout, app availability tied to DDL, migration drift across instances, and limited rollback traceability. | Move schema changes to an explicit ordered migration/release step; ensure each migration is reversible where practical, tested against a copy, and never destructively applied automatically on web startup. |
| R-04 | **P1 / High** | Full baseline: 301 collected, 269 passed, 32 failed, 35 warnings. Failures touch risk/consensus, paper trading, Telegram, VIP, MT5 and metadata contracts. | New work can mask existing defects; current product behavior and tests disagree in safety-sensitive flows. | Triage every baseline failure, distinguishing outdated expectations from defects. Preserve fail-closed behavior unless an evidence-backed change is approved. Add deterministic fixtures and re-run the entire suite before each phase release. |
| R-05 | **P1 / High** | Login rate limiter, market caches, MT5 received ticks, registry status, monitor thread and some dedup locks are process-local. Render blueprint currently declares one web instance. | Horizontal scale/restart can reset limits, statuses/caches, scanner leases, or duplicate notification reservations. | Keep one instance until workloads justify scale; make required quota, notification idempotency, locks and execution history database-backed/atomic before scaling. Add multi-worker tests and metrics as a phase gate. |
| R-06 | **P1 / High** | Agent registry exposes 17 entries but most are deterministic local algorithms; timeout/retry settings are metadata and must be verified at the execution boundary. Some state is a process singleton. | UI/reporting can overstate model calls, live execution states, or independent consensus; stuck tasks may block scans if timeouts are not enforced by callers. | Map 16 requested roles to existing code; require per-execution IDs, actual start/end events, source/time, errors and truthful statuses. Enforce deadlines, cancellation/failure isolation, and independent risk veto with tests. |
| R-07 | **P1 / High** | Data depends on external feeds and a Windows MT5 bridge. Quotes, candles, calendars and spread can be missing/stale; the code correctly has fail-closed paths. | Users can mistake delayed/reference data for broker execution prices, or receive no signal during outages. | Preserve source/timestamp/freshness on every current-price claim. Keep XAUUSD MT5 priority when fresh; show OANDA/reference source separately; never synthesize. Add per-source status and failover/market-closed tests. |
| R-08 | **P1 / High** | Render config points ABA to sandbox; no live merchant transaction was performed in this audit. Repo integration notes describe an earlier small sandbox check. | Checkout may be unavailable or misconfigured in production; test evidence does not prove paid callback delivery, entitlement, refunds, or recurring billing. | Keep sandbox; confirm official ABA merchant configuration/signature and callback allow-list, run full sandbox payment/callback/duplicate tests, then separately review live credentials. No automatic charge without ABA approval and consent. |
| R-09 | **P1 / High** | Cumulative docs describe different agent counts/capabilities; actual registry/UI/routes are broader or narrower than some README claims. | Product roadmap, support, UI status, and trading risk representations can drift from actual behavior. | Treat code + tests + verified provider records as source of truth. Maintain these inventory docs and require claims-to-evidence review in each phase. |
| R-10 | **P2 / Medium** | Frontend has no build manifest, unit/component/browser tests, WebSocket client/server, service worker, or manifest found; chat responses are request/response JSON. | Responsive/accessibility/loading/realtime claims are difficult to validate and streaming/PWA acceptance is unmet. | Establish minimal UI regression/accessibility/viewport coverage before broad redesign; only add streaming/PWA infrastructure after measurement and deployment support. |
| R-11 | **P2 / Medium** | Backtest jobs and learning records exist, but no complete dataset/model registry, walk-forward promotion gates, or versioned experiment contract was confirmed. | In-sample or unversioned results can be mistaken for validated predictive performance. | Require immutable dataset/strategy versions, transaction costs, out-of-sample/walk-forward results, and bias checks before promoting strategies. Never label weight/prompt tuning as model training. |
| R-12 | **P2 / Medium** | Paper trade ledger and lifecycle tables exist, but no complete standalone trading journal (notes, screenshot attachments, tags, verified analytics) was found. | Requested journal scope is not met; users may treat paper records as broker-imported results. | Label data origin; add a separate, user-isolated journal model and analytics only with reversible migrations and persistence tests. |
| R-13 | **P2 / Medium** | Python dependencies are minimum-bounded, with no lockfile; web assets are hand-versioned in HTML. No CI workflow was found in visible repository files. | Builds can drift, and deployment may not have a repeatable automated verification gate. | Add lock/CI after dependency audit; pin compatible ranges, run tests/security checks and static assets version checks in CI. Do not add infrastructure without cost justification. |
| R-14 | **P2 / Medium** | Signals/monitoring run inside the web process; Render blueprint uses a single free-plan web service. Background monitoring availability follows that process/host uptime. | Web restarts or host sleep can pause scans; web request load and background work share resources. | Show monitor heartbeat and degraded/unknown status; verify actual host behavior. Only split workers or add queue infrastructure after measured load supports it. |

## Immediate deployment gate

The R-01 mitigation is implemented locally and the focused suite passed 21 tests with 2 deprecation warnings. The current Render revision has not been changed. Do not deploy until staging verification and review are complete. No production database writes or provider charges were made.
